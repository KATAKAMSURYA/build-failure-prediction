## 1. Introduction

Modern software teams push hundreds of commits every day. Each commit triggers an automated **build** – a process that compiles code, runs tests, and produces a deployable artefact. When builds fail, the entire team is blocked and delivery slows down.

This project uses **Machine Learning** to predict whether a build is likely to fail *before* it runs, giving developers an early warning so they can fix issues proactively.

---

## 2. Problem Statement

Software builds fail for various reasons:

- Too many files changed in a single commit (large, risky diff).
- Very few or no test files updated alongside production code.
- Commits pushed late at night when attention is reduced.

Traditional CI/CD pipelines only tell you a build has failed *after* wasting compute time. An AI-based prediction system can flag risky builds *before* they run, reducing wasted resources and developer frustration.

## 6. Dataset Description

> ⚠️ **This dataset is entirely synthetic (simulated) data generated by `ml/generate_dataset.py`. It does NOT represent real company production data. It is created solely for educational demonstration purposes.**

The dataset contains **300 build records** with the following columns:

| Column | Type | Description |
|--------|------|-------------|
| `files_changed` | Integer | Number of source files modified in the commit |
| `lines_changed` | Integer | Total lines of code added or removed |
| `tests_touched` | Integer | Number of test files modified alongside production code |
| `hour` | Integer | Hour of day when the build was triggered (0–23) |
| `failed` | Integer | **Target**: 1 = build failed, 0 = build passed |

---

## 7. Explanation of Input Features

### 7.1 `files_changed`
When a developer modifies many files in a single commit, the risk of introducing a bug increases. A change spanning 15 files is far riskier than a 2-file hotfix.

### 7.2 `lines_changed`
Large diffs (many lines added/removed) are harder to review and test. Research shows that larger code changes correlate with more defects.

### 7.3 `tests_touched`
If production code changes without corresponding test updates, the new behaviour may be untested. Zero test changes alongside 400 lines of production code is a red flag.

### 7.4 `hour`
Commits pushed late at night (e.g., 10 PM–2 AM) are associated with reduced attention and higher error rates. The model uses the build trigger hour as a proxy for commit quality.

## 8. Machine Learning Algorithm – Random Forest Classifier

A **Random Forest** is an ensemble of many Decision Trees. Here is how it works:

```
                        ┌─────────────────────────┐
                        │   Build Feature Vector   │
                        │  files, lines, tests, hr │
                        └────────────┬────────────┘
                                     │
              ┌──────────────────────┼──────────────────────┐
              │                      │                      │
        ┌─────▼─────┐          ┌─────▼─────┐         ┌─────▼─────┐
        │  Tree 1   │          │  Tree 2   │  . . .  │  Tree 100 │
        │  FAIL     │          │  PASS     │         │  FAIL     │
        └─────┬─────┘          └─────┬─────┘         └─────┬─────┘
              │                      │                      │
              └──────────────────────┼──────────────────────┘
                                     │
                              Majority Vote
                                     │
                              PREDICTION: FAIL
```

**Why Random Forest?**
- Handles non-linear relationships between features.
- Robust to outliers and noisy data.
- Provides feature importance scores.
- Does not require feature scaling.
- Excellent accuracy with minimal hyperparameter tuning.

## 10. Model Evaluation

The model is evaluated using:

| Metric | Description |
|--------|-------------|
| **Accuracy** | % of total predictions that are correct |
| **Precision** | Of all predicted failures, how many were real? |
| **Recall** | Of all real failures, how many did we catch? |
| **F1-Score** | Harmonic mean of precision and recall |
| **Confusion Matrix** | Table of true/false positives and negatives |

## 15. Advantages

1. **Early warning** – Flags risky builds before wasting CI compute time.
2. **Simple and interpretable** – Feature importance shows exactly *why* a build is risky.
3. **No external APIs** – Runs entirely offline with open-source libraries.
4. **Automated** – GitHub Actions runs the full pipeline on every push.
5. **Reproducible** – Fixed random seed ensures consistent results.

---

## 16. Limitations

1. The model is trained on **synthetic data**, not real historical build logs.
2. Only **4 features** are used; real systems use dozens (dependency changes, branch age, author experience, etc.).
3. Random Forest is not a real-time streaming model; it predicts in batch.
4. The 15 % / 50 % / 85 % thresholds are illustrative and not calibrated for any real project.
